### 3.3 中断节拍实现

```asm
08000dda <SysTick_Handler>:
  push  {r3, lr}
  bl    8000994 <chassis_tick>        ← 采样 + 斜坡 + PID + PWM
  bl    800170c <protocol_tick_flag>  ← 仅 tick_cnt++
  pop   {r3, pc}
```

确认 1 kHz 中断里**没有任何字符串操作或浮点格式化**，符合设计意图。

### 3.4 栈占用

```
单函数最大栈深度：112 字节 (protocol_poll)
```

1 KB 栈有充足余量（约 9 倍）。中断嵌套（SysTick + USART1）最坏情况也在 300 B 以内。

### 4.1 PID 参数是怎么定下来的

初始版本 `Kp=1800, Ki=90` 是拍脑袋给的，测试直接失败（目标 0.3 m/s，实际只到 0.074）。

于是写了参数扫描 `tests/host/pid_sweep.c`，用与固件一致的被控对象模型
（一阶惯性 + 真实死区 180）扫描 3 个目标速度 × 6 个 Kp × 5 个 Ki：

**发现 Kp=1800 / Ki=20000 在 0.1~0.6 m/s 全速域满足：**
- 超调 ≈ 0%
- 稳态误差 ≈ 0
- 调节时间 0.87 s（0.3 m/s 目标）

这组值已写入 `board.h` 的默认参数。

### 4.2 顺带修掉的一个设计缺陷

初版 `motor.c` 里写了"死区补偿"：任何非零占空比都抬到 180。
扫描发现这会让系统卡死 —— PID 输出落在 (0, 180] 区间时执行器恒定输出 180，
输出不连续，积分项失去意义，形成极限环，小目标速度根本收不住。

**已改为**：执行器保持线性，死区交给 PID 积分项自己顶过去。
稳态时积分正好等于死区电压，这是增量式 PID 的天然优势。

## 5. 未能验证的部分（需要实物）

以下必须在真实硬件上确认，软件层面无法替代：

| 项目 | 原因 |
|---|---|
| PWM 波形 | 需示波器看 PB6/PB7 是否有 20 kHz 方波 |
| 编码器计数 | 需实际转轮子，确认 AB 相和计数方向 |
| 电机转向 | 需上电看轮子转向，反了就调线或改代码 |
| PID 实车表现 | 仿真模型 ≠ 真实电机，必须按 README 第 5 章重整定 |
| 电源抗扰 | 需实测电机启动时单片机是否复位 |
| 串口通信 | 需 USB-TTL 实测波特率是否准确 |

## 6. 复现构建

```bash
cd firmware
python build.py --clean
```

若工具链不在 `D:\armgcc\toolchain`，脚本会自动搜索 PATH、PlatformIO 包目录等位置。
它优先选择**纯 ASCII 路径**下的编译器，以规避上述 GCC 缺陷。
